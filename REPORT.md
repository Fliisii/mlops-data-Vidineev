## 4. Сравнение Git/DVC и ClearML

| Критерий | Git + DVC | ClearML |
|---|---|---|
| Основное назначение | Совместное версионирование кода и данных | Управление датасетами и их версиями в ML-проектах |
| Метаданные | Файлы `.dvc`, конфигурация DVC и история Git | Метаданные датасетов и связи между версиями |
| Хранение данных | В DVC cache и настроенном remote | В хранилище, настроенном для ClearML |
| Связь версий | Через Git-коммиты, ветки и DVC-метаданные | Через родительские версии датасетов |
| Восстановление | `dvc pull` получает данные из remote; `dvc checkout` переключает данные согласно текущим метаданным DVC | Загрузка конкретной версии датасета |
| Преимущества | Связь данных с кодом, прозрачная история изменений, интеграция с Git | Удобная работа с версиями датасетов и их происхождением |
| Ограничения | Требуется доступное хранилище данных; локальный remote не подходит для совместного восстановления через интернет | Требуется доступ к серверу ClearML и соответствующему хранилищу |

Git и DVC удобно использовать, когда изменения данных необходимо связывать с изменениями кода. ClearML предоставляет отдельный механизм управления датасетами и их происхождением. Инструменты решают схожие, но не полностью одинаковые задачи и могут использоваться совместно.

## 5. Ответы на контрольные вопросы

### 1. Как определить, какая версия данных соответствует конкретному коммиту Git?

В истории Git необходимо найти нужный коммит и проверить состояние файлов `.dvc` в этом коммите. Эти файлы содержат контрольные сведения, позволяющие DVC определить соответствующие версии данных. После восстановления из доступного хранилища можно проверить содержимое файлов и их контрольные суммы.

### 2. Где физически хранятся данные при использовании Git и DVC? Для чего нужен DVC remote?

Git хранит историю исходного кода и небольшие текстовые файлы метаданных DVC. Сами большие файлы данных хранятся в DVC cache и в настроенном DVC remote. Remote нужен для хранения объектов данных вне истории Git и их получения при восстановлении проекта. В этой работе использовался локальный remote.

### 3. Как создать новую версию датасета в ClearML и получить её ID?

Для этого создают объект `Dataset`, задают имя, проект и при необходимости родительский датасет. Затем добавляют или изменяют файлы, финализируют версию и получают её ID. ID позволяет однозначно ссылаться на конкретную версию датасета.

### 4. Для чего используется метод `finalize()` при работе с датасетами ClearML?

`finalize()` завершает подготовку версии датасета и фиксирует её как готовую для дальнейшего использования. После финализации версия рассматривается как завершённая, а изменения следует оформлять отдельной версией, а не продолжать менять уже опубликованную.

### 5. Как проверить родительские версии датасета в ClearML?

Можно получить объект датасета по его ID и проверить связи с родительскими версиями с помощью соответствующих методов API ClearML, например `_get_parents()`. В работе этот способ использовался для проверки родительских связей версий `1.0.0`, `1.1.0` и `2.0.0`.

### 6. Для чего используется команда `dvc checkout` и чем она отличается от `dvc pull`?

`dvc checkout` приводит файлы данных в рабочем каталоге в соответствие с текущими DVC-метаданными, используя доступные локальные объекты. Это полезно при переключении между версиями Git.

`dvc pull` получает необходимые объекты из настроенного удалённого хранилища и восстанавливает данные в рабочем каталоге. Поэтому для восстановления данных в чистом клоне, когда нужных объектов ещё нет локально, обычно используют `dvc pull`.

### 7. В чём основные различия между DVC и ClearML при версионировании данных?

DVC тесно интегрирован с Git и позволяет связывать версии данных с коммитами и ветками кода. ClearML организует версии датасетов в рамках ML-проекта и позволяет отслеживать их идентификаторы и родительские связи. DVC особенно удобен для воспроизводимости состояния репозитория, а ClearML — для управления датасетами в ML-процессах. Выбор зависит от инфраструктуры и требований проекта.
